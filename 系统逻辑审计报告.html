一句话总评： 系统的"骨架"已经搭起来——资产台账、公寓、厂房租售、合同、收费、抄表、客户、商户、工单、系统设置十大域都在，且已导入了 188 个单元 / 113 个客户 / 147 份生效合同 的真实台账。但从"总经理决策口径"看，有 2 个会直接误导经营判断的指标级 BUG，以及一条"合同→账单→收款"主营收线几乎没数据驱动的断点。表单整体偏"录入薄"，多处主数据未打通。建议先做 P0 三个口径修复，再补关联，最后做表单增厚。

一、已打通的逻辑（值得肯定的部分）

  • 资产↔合同↔客户 主链基本通： units.current_contract_id / current_customer_id 指针齐全，仅 1 个异常单元（已定位）。资产台账、厂房租赁/销售、合同三处可互查。
  • 抄表↔资产已关联： /api/meter-units 以签约生效合同派生 149 个"应抄表单元"（公寓 109 + 厂房租赁 9 + 厂房销售 31），抄表记录通过 unit_id 双向关联到资产/公寓/厂房详情。
  • 水电抄表↔收费账单联动已落地（方案 B）： 抄表"生成账单"会把水电金额按"水费/电费"两条拆账写进 apartment_fees，并幂等。
  • 合同状态机相对完整： 签约自动联动单元状态（在租/已售）、续租（保留原合同指针）、退租（单元置空 + 押金/末月租金/末月水电结算开口）。
  • 看板 KPI 维度齐： 出租率、间夜出租率、销售去化率、应收/已收/欠费/收缴率、营收趋势、工单统计都有聚合。

二、核心逻辑缺陷（直接影响经营决策，必须修）

🔴 P0-1　公寓出租率 / 出租数 指标失真（肉眼可见）

现象： 看板上"公寓出租率"会显示约 1.7%，但真实占用是 110/117（94%）。

根因： 仪表盘 api_dashboard._kpis() 用 st.get("在租") 计数出租套数；而导入的公寓单元状态是 "在住"(108) + "在租"(2) + "空置"(7)。108 套"在住"不被计入 → 出租率≈2/117。

连锁： 同一个"公寓出租"数据，在 公寓管理 页 summary 却显示"当前在住 108"（按合同算，正确），看板与子模块口径打架，总经理一眼就能看出矛盾。

修复方向： 公寓出租口径应统一按"占用 = 在住 + 在租"或按合同数；并统一单元状态字典（"在住"并入"在租"语义）。

🔴 P0-2　"合同→账单→收款"主营收线几乎空转

数据实测： 147 份生效合同，全库仅 2 笔账单（覆盖 1 份合同）；应收、收缴率、欠费分析因此基本无数据支撑。

根因：

  • 账单生成入口 generate_monthly_bills 从未被批量执行过（需点"生成月度账单"，且当前只点了 1 次）；
  • 更致命：108 份公寓合同（HT-AP）金额全部 = 0。公寓真实月租在 apartment_rentals.monthly_rent 里有值，但没有回流到合同 amount，导致即便生成账单也是 0 元，方案 B 同步到公寓收费的也是 0。

影响： 财务"收费"页、看板"应收/欠费/收缴率"对总经理基本是空壳；公寓"水电费"无法体现真实租金口径。

修复方向： ① 公寓合同 amount 回填为对应房间月租合计；② 上线"按月批量生成账单"并提供一键跑全量历史；③ 生成前校验金额>0。

🔴 P0-3　厂房 rentable / sellable 标记与状态不一致

数据实测： 厂房 71 套——在租 8、已售 30、空置 22、自持 11；但 rentable=1 仅 30 套、sellable=1 仅 22 套。即 30 套"已售"中，只有 22 套被标记为可售，8 套已售厂房 sellable 仍为 0；自持 11 套的租售标记也未归一。

影响： 看板"厂房出租率/去化率"分母依赖这两个标记，口径失真且难以复核。需在导入/状态变更时让 status 与 rentable/sellable 联动一致。

四、表单过于简陋（按模块列字段缺口）

🏢 资产单元（核心表单，最薄）

现有：编号/楼栋/业态/面积/月租金/售价/可租/可售/状态。

缺： 楼层号、用途（生产/办公/仓储）、交付标准、朝向、建筑面积 vs 计租面积、层高/承重、设备清单、关联楼栋楼层。
影响：资产台账无法支撑面积去化、设备盘点、招商定价。

📄 合同（新建偏薄）

现有：合同号/客户/金额/周期/起止/押金。

缺： 免租期（free_days 有字段未用）、签约日期（写死 today 不可改）、经办人、租金递增条款、销售分期/按揭方式、保证金条款、附件、备注（被 type 占位）。
影响：财务/法务口径缺失，合同文本不可追溯。

🔧 工单（最简）

现有：工单号/类型/报修人/处理人/描述/状态。

缺： 关联单元（字段有 unit_id 但未暴露）、优先级、期望完成时间、实际完成时间、维修费用、满意度评分（rating 字段浪费）、派工记录。
影响：无法做"单元维度报修热力"和 SLA 考核。

👤 客户（尚可，有漏洞）

现有：类型/名称/联系人/电话/业务线/阶段/渠道/来源/负责人/行业/需求/预算/标签/地址。

缺： 企业信用代码 / 个人身份证号（新建时无录入框，仅在编辑时搬旧值）、开票信息、关联合同/资产下钻。
影响：财务开票、风控缺证照。

💰 收款（偏简单但可接受）

现有：金额/日期/方式/凭证号。

可补： 冲抵哪一期、部分收款备注、是否有滞纳金一并收取。

⚙️ 系统人员（小问题）

角色用自由文本输入框，可输入任意值，与 sys_roles 表脱节；部门/角色应以下拉联动。

抄表表单相对完整（水/电双表、用量自动算、费用预览、CSV 导入导出），但单价默认 3 元/吨、1.5 元/度是硬编码，应取自系统规则或单元定价。

五、数据健康度（冗余与脏数据）

  • 双公寓模型并行： 旧表 apartment_records 仍残留 5 条种子数据，前端不用但 API 仍可写——存在脏数据风险，建议删除旧表或冻结写入。
  • 双抄表表并行： 旧表 meter_readings 残留 2 条 demo 数据（新建抄表走 meter_reading_records），建议清理。
  • 自动生成客户： 110 个公寓客户由 _migrate_apartment_contracts 自动建，address='园区公寓'、无工商信息——属于"系统派生客户"，应与真实招商客户区分/合并。
  • 单元状态字典不统一： 公寓用"在住/在租/空置"，厂房用"在租/已售/空置/自持"，资产台账筛选下拉却是另一套（含装修中/锁定）——三处枚举不一致。

六、优先级整改路线图

🟢 P0（立即，影响决策真实性）

  • ① 修复公寓出租率口径（看板与子模块统一按"占用=在住+在租"或按合同数）。
  • ② 公寓合同 amount 回填为房间月租合计；并补一段"按合同批量生成历史账单"脚本，跑通 147 份合同的应收。
  • ③ 校验并归一厂房 rentable/sellable 与 status 的一致性。

🟡 P1（关联打通，1~2 周）

  • 商户由合同派生、客户详情加"合同/资产/应收"下钻、工单关联单元、押金由合同动作自动产生、关键操作落审计、后端权限校验。

🔵 P2（健壮性/体验，后续）

  • 清理双模型旧表、系统规则驱动到期/滞纳金、数据字典接管下拉、市场调研转线索、表单字段增厚（单元/合同/工单/客户证照）。

以上均为"只读审计"，未改动任何代码与数据。确认整改范围后，我可按 P0→P1→P2 顺序逐批实施并回测。
